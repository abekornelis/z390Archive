This document will explain how a Block in a zVSAM file is structured.

A Block can be any size between 4096 bytes (4 KB) and 1,048,576 bytes (1 MB)
Up pto 256 records can be stored in a Block.
If a Block holds 256 records and is not full, the remaining space is unusable,
except for extending existing records (if they are Variable-length records)
within the Block. Thus, large Block sizes can waste considerable amounts of space.

Each Block has a Block Header and a Block Footer.

Here we'll work out an example for an ESDS with a Block size of 4096 bytes,
holding spanned records with variable lengths, and therefore preceded by a RDW.
Each segment is also preceded by a SDW.
Unspanned records as used in the ESDS_V example waste around 7% of available space in
every 4096-byte Data Block. Using Spanned records, we'll be able to use all
available space in the Data Blocks at the expense of adding a SDW for each
segment of the records in the file. On average, every sixth record will have
two segments, so we'll be wasting 6*4=24 bytes per Block, which is roughly 0.6%.

The first, unaddressable Block in the file is a Prefix Block, followed by
Block 0, which is used as a spacemap Block.

648, 655, 689, 649, 1175, 744, the data would be on Blocks 1 through 3 as follows:

BHDREYE  is an EYE-catcher to identlfy the start of the Block Header.
         It's value is always the characters 'HDR'

BHDRVER  Is a one-byte version indicator, used to enable backward
         compatability from future design versions. The current version is 1.

BHDRSEQ# is a one-byte sequence number, incremented each time the Block
         is written. When the counter reaches 256 it wraps back to zero.
         It is kept in sync with BFTRSEQ#. Whenever they are not equal,
         the Block has not been written completely and will be regarded
         as damaged.

BHDRFLGS is a one-byte flag field containing the Block type.
         For a data Block, the value is X'20'.

BHDR#REC is a one-byte field containing the number of records present
         in this Block. Block 1 holds five complete records plus the
         first segment of record 6. So we have 6 entries in the RPTR table.
         Block 2 holds the second segment of record 6, plus 5 more records.
         So Block 2 also contains 6 RPTR entries. Had record 11 been
         shorter, we'd have had a seventh entry.
         Block 3 contains only an entry for record 12; the value is 1.

BHDRXLVL is used only for index components. For an ESDS it contains zeros.

BHDRSELF is to double-check the file has not been damaged.
         it contains the Block's own XLRA - a 7-byte Block address
         with a byte of zeros appended.
         The first four bytes of zeroes are not shown in the table above.

BHDRNEXT points to the next logical Block on the Data Block chain.
         In an ESDS this should normally be the physical
         sequence of Blocks (with the exception of an occasional
         intermittent spacemap Block. Thus the Prefix Block field
         PFXBDATA points to Block 1 (Block 0 is a spacemap Block),
         Block 1 points to Block 2, Block 2 points to Block 3, etc.
         The last Block on the chain has foxes to indicate end of chain.
         The first four bytes of zeroes are not shown in the table above.

BHDRPREV points to the preceding logical Block on the Data Block chain.
         In an ESDS this should normally be the reversed physical
         sequence of Blocks (with the exception of an occasional
         intermittent spacemap Block. Thus the Prefix Block field
         PFXEDATA points to Block 3, Block 3 points to Block 2,
         Block 2 points to Block 1, which holds foxes to indicate end
         of chain. Block 0 is a spacemap Block and does not reside
         on the Data Block chain.
         The first four bytes of zeroes are not shown in the table above.

BHDRFRE@ is a three-byte pointer to the available freespace area in the Block.
         Since records are allocated starting from the end of the Block,
         the free space area starts after the pointer table's terminating entry.
         Block 1 has no free space left, so the value is 0.
         Block 2 has 6 bytes of free space left. Not enough to create a segment.
         Therefore these bytes are left unused.
         Block 3 holds 1 record, so the pointer table holds 2 entries of 4 bytes
         each. Freespace starts at 40 + 8 = 48 or X'30'.

BHDRFREE is a three-byte field holding the amount of available freespace in the Block.
         Block 1 has no free space left, so the value is 0.

--       The last two bytes of the header are unassigned and contain zeroes.

RPTRTBL  indicates the start of the pointer table.

RPTRTBL[0]
RPTRFLGS flags of first pointer. X'00' indicates a normal record pointer. 
         X'10' occurring only on Block 2, is used to indicate a non-first segment.
RPTRREC@ pointer to first segment's SDW on the Block.
         The first segment/record is allocated 694 bytes (the record's length, plus 4 bytes
         for the record's RDW, plus 4 bytes for the SDW) down from the start of the
         Block Footer. 4096 - 4 - 694 = 3398 or X'D46'.
         On Block 2, the first segment holds the remainder of record 6, which is 686 bytes long,
         524 bytes being in the first segment, 162 remain for the second segment.
         Thus, the first segment on Block 2 is the second or final segment of record 6.
         It holds no RDW, the RDW is included in the first segment.
         Therefore the first segment on Block 2 is allocated 166 (for record data + SDW)
         bytes down from the Block's footer: 4092 - 166 = 3926 or X'F56'.
         On Block 3, the first record is 744 bytes long, so is allocated 752 bytes
         down from the Footer. 4092 - 752 = 3340 or X'D0C'

RPTRTBL[1]
RPTRFLGS flags of second pointer. X'00' indicates a normal record pointer.
         On Block 3 the second record has not yet been created, so here the
         value will be X'FF' = termination entry.
RPTRREC@ pointer to second segment's SDW on the Block.
         The second segment/record is 695 bytes long, so it is allocated 703 bytes
         down from the preceding record. 3398 - 703 = 2695 or X'A87'.
         On Block 2, the second segment is 648 bytes long, so is allocated 656 bytes
         down from the preceding record. 3926 - 656 = 3270 or X'CC6'
         In Block 3 the value will be foxes to indicate the termination entry.

RPTRTBL[2] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS flags of third pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to third segemnt's SDW on the Block.
         The third record is 712 bytes long, so it is allocated 720 bytes down
         from the preceding record. 2695 - 720 = 1975 or X'7B7'.
         On Block 2, the third segment is 655 bytes long, so is allocated 663 bytes
         down from the preceding record. 3270 - 663 = 2607 or X'A2F'

RPTRTBL[3] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS flags of fourth pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to fourth segment's SDW on the Block.
         The fourth segment/record is 677 bytes long, so it is allocated 685 bytes down
         from the preceding record. 1975 - 685 = 1290 or X'50A'.
         On Block 2, the fourth segment is 689 bytes long, so is allocated 697 bytes
         down from the preceding record. 2607 - 697 = 1910 or X'776'

RPTRTBL[4] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS flags of fifth pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to fifth segment's SDW on the Block.
         The fifth segment/record is 682 bytes long, so it is allocated 690 bytes down
         from the preceding record. 1290 - 690 = 600 or X'258'.
         On Block 2, the fifth segment is 649 bytes long, so is allocated 657 bytes
         down from the preceding record. 1910 - 657 = 1253 or X'4E5'

RPTRTBL[5] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS flags of sixth pointer. X'00' indicates a normal record pointer.
RPTRREC@ For Block 1, the next record is 686 bytes long, yet the Block has
         only 600 - 68 = 532 bytes of free space availalble. From this free space
         we need to reserve 8 bytes for SDW and RDW. 524 bytes are left for 
         record data. Thus, record 6 will be split into two segments, the first
         holds 524 bytes of data, the remainder goes on the next logical Block.
         Thus, the sixth pointer will hold a value of 68 or X'44' pointing
         directly after the record pointers table.
         On Block 2, the sixth segment is 1175 bytes long, so is allocated 1183 bytes
         down from the preceding record. 1253 - 1183 = 70 or X'46'

RPTRTBL[6] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS termination entry for table of record pointers. Value X'FF'
RPTRREC@ The table of record pointers is terminated with an entry containing foxes.

--       The freespace area varies both in starting location and in length.
         It is absent from Block 1; on Block 2 a tiny amount of 6 bytes is left free.
         These six bytes are not enough to accomodate a SDW+RDW plus at least 8 bytes
         of record data. Therefore these bytes are left unused.

data[4]  fifth record, present on Blocks 1 and 2, not on Block 3
data[3]  fourth record, present on Blocks 1 and 2, not on Block 3
data[2]  third record, present on Blocks 1 and 2, not on Block 3
data[1]  second record, present on Blocks 1, 2, and 3
data[0]  first record, present on Blocks 1, 2, and 3

BFTREYE  is an EYE-catcher to identlfy the end of the Block.
         It's value is always the characters 'FTR'

BFTRSEQ# is a one-byte sequence number, incremented each time the Block
         is written. When the counter reaches 256 it wraps back to zero.
         It is kept in sync with BHDRSEQ#. Whenever they are not equal,
         the Block has not been written completely and will be regarded
         as damaged.

===================================================

--> Open

When the dataset is opened, the Prefix Block is read and validated.
The validations are described in the zVSAM_design document.

===================================================

--> Get (sequential)

Segmented records are returned to the application 1 record at a time.
Desegmentation is performed by VSAM before returning the record to the application.

When getting a record, the RPL holds the XLRA of the last record retrieved.
From the RPL's last XLRA the next RPTRTBL entry is located.
If the RPTRTBL entry is not a termination entry, the pointer is used
to retrieve the associated segment.
If a termination entry is encountered instead, then the Block's BHDRNEXT
pointer is used to access the next Block in the list of Data Blocks and the
first entry on that Block's pointer table is used to retrieve the associated segment.

After retrieving the first segment, if it is the only segment, then the record
is conctructed by removing the SDW, and the record is returned to the application.
Otherwise (it is not the only segment) subsequent segments are retrieved until the
last segment of the record has been read. All segments (without the SDW) are concatenated
to reconstruct the complete record image, which is then returned to the application.

--> Get (backward)

When getting a record, the RPL holds the XLRA of the last record retrieved.
From the RPL's last XLRA the preceding RPTRTBL entry is located if the XLRA has
a XLRAREC other than 0. If the XLRAREC is 0, the Block's BHDRPREV pointer is
used to access the preceding Block. Subsequently, that Block's BHDR#REC is used to
access the last record segment in that Block.

After retrieving the last segment, if it is the only segment, then the record
is conctructed by removing the SDW, and the record is returned to the application.
Otherwise (it is not the only segment) preceding segments are retrieved until the first
segment of the record has been read. All segments (without the SDW) are concatenated to
reconstruct the complete record image, which is then returned to the application.

===================================================

--> Put (add new record)

The last Block on the chain of Data Blocks is accessed, using the Prefix Block's
PFXEDATA pointer. If the Block is already in a buffer this step can be skipped.

If fewer than 16 bytes of free space are available on the Block, allocation
proceeds to next logical Block. 

A new record entry is allocated from the free-space area and a new record pointer
overwrites the existing termination entry. A new termination entry is added to the
table of record pointers.

The Header is updated to reflect the decrease in free space:
BHDRFRE@ is incremented by 4 (the length of the new pointer table entry)
and BHDRFREE is decremented by the pointer table entry length, the SDW+RDW lengths,
and as much of the record's length as will fit in the remaining free space.

If insufficient free space is available to hold the entire record+SDW+RDW, then only a first
segment is stored and a new Block is added to the end of the Data Block chain.
The full Block's BHDRNEXT pointer will be adjusted to point to the new Block,
the new Block's BHDRPREV will be set to point to the full Block, and the Prefix Block's
PFXEDATA pointer will be set to point to the new Block.

The remaining fields in the new Block's Header and Footer will be initialized,
and the first entry in the record pointer list will be created, followed
by a termination entry. The next segment of the record can then be split off it: each
segment+SDW (RDW only in first segment) will use up all remaining free space in its Block.

The Spacemap Block covering the filled Block will be updated to reflect the
Data Block being filled. The spacemap Block covering the new Block (normally the
same Spacemap Block, but might be the next Spacemap Block) will be updated
to reflect that this Block is in use and partially filled.

The process is repeated until the last segment of the record has been stored.

--> Put (update existing record)

Case 1: length does not change
        The record is segmented to match the exising segments in the file.
        Each segment of the record is overwritten in its own Block.
        No other changes are needed.

Case 2: length decreases
        The record is segmented to match the exising segments in the file.
        The number of segments may decrease, the last segment of the new
        record may be shorter than it was before, or it may be the same length.
        The RDW is adjusted, and so is the SDW of the final segment.
        All segments that do not change length simply overwrite the prior verision.
        If the last segment of the new record did not change length, then
        it overwrites the prior version. If its length is reduced, then it will
        be reallocated so that its end address does not change.
        Thus, its SDW will move up by the number of bytes the segment has been
        shortened. The pointer in the pointer table is adjusted accordingly.
        Subsequently, all records allocated to a lower address than the
        updated segment are moved up by the same number of bytes and their
        pointers are updated accordingly. Finally, the amount of free space
        is incremented by the number of bytes the segment has been shortened.
        Any remaining segments of the old record (the ones no longer needed)
        will be converted to free space. If the segment is the only segment on
        the Block, the Block will be marked unallocated in the spacemap.
        Otherwise, the segment pointer is removed from the Block's pointer list.
        Subsequently, all records allocated to a lower address than the
        removed segment are moved up by the number of bytes freed and their
        pointers are updated accordingly. Finally, the amount of free space
        is incremented by the number of bytes the segment has been shortened.

Case 3: length increases, enough freespace is available.
        The record is segmented to match the exising segments in the file.
        The final segment is extended by at most the amount of bytes
        available as free space on it's Block. The RDW in the first
        segment is adjusted to reflect the new length of the record.
        All non-last segments are overwritten.
        The last segment has its SDW updated to reflect the larger length.
        The old segment is removed from the Block by moving all segments residing
        at a lower offset than the segment to be updated up by the old length of the
        segment. Their record pointers are adjusted accordingly.
        The new version of the updated final segment is allocated from the enlarged
        freespace in the Block and its pointer adjusted to match its new location.
        The amount of freespace in BHDRFREE is decreased accordingly.
        Mark that the pointer to the segment is not reallocated: it retains
        its position in the table of record pointers. Thus, all segments retain
        their XLRA, even though the final or only segment now resides at a different
        offset in the Block.

Case 4: length increases, not enough freespace is available.
        The record is segmented to match the exising segments in the file.
        The last segment of the old record is extended - if possible - to use
        all remaining free space in it's Block. Additional whole-Block segments
        are added until not enough data remains to fill a whole-block segment.
        The remaining data - if any - are used to create a final segment.
        The RDW in the first segment is updated to reflect the new length.
        All non_last segments of the old record are overwritten.
        The last segment of the old record is reallocated (see case 3 above
        for details of the reallocation logic).
        The added segment(s) require new Blocks to be inserted into the logical
        chain of data Blocks. There are four scenarios to cover this case:
        1. the old record had a single segment, which is not the last record
           on it's Block. In this case the record is displaced to a new Block,
           or a series of new Blocks if the new record is too long to fit on a
           single Block
        2. the old record had a single record which was the last segment
           on it's Block. In this case the old segment can be lengthened to
           consume all remaining free space on the Block (if any).
           The new segments can go onto new Blocks that are inserted after the
           Block that held the old record/segment.
        3. the old record had multiple segments, the last one was the only one
           on it's Block. This case handled analogously to case 2 above.
        4. the old record had multiple segments, the last one was not the only one
           on it's Block. In this case the final segment of the old record is
           displaced to prevent its fake XLRA from being reused.
           The displaced segment goes to a new Block, from this point onward
           the case can be handled analogously to cases 2 and 3 above.

===================================================

--> Erase

Erase is not supported for ESDS datasetets.

To remove unneeded records, the dataset needs to be unloaded,
then reloaded with relevant data records only.

===================================================

--> Point

A point will set the indicated XLRA current. A subsequent sequential
read will return the the record with the indicated XLRA.
A point to a fake XLRA will be deemed invalid.
