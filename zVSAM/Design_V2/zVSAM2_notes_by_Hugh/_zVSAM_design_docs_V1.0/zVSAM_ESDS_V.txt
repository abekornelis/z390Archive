This document will explain how a Block in a zVSAM file is structured.

A Block can be any size between 4096 bytes (4 KB) and 1,048,576 bytes (1 MB)
Up pto 256 records can be stored in a Block.
If a Block holds 256 records and is not full, the remaining space is unusable,
except for extending existing records (if they are Variable-length records)
within the Block. Thus, large Block sizes can waste considerable amounts of space.

Each Block has a Block Header and a Block Footer.

Here we'll work out an example for an ESDS with a Block size of 4096 bytes,
holding records with variable lengths, and therefore preceded by a RDW.
The first, unaddressable Block in the file is a Prefix Block, followed by
Block 0, which is used as a spacemap Block.
Assuming 12 records in the file with lengths 686, 695, 712, 677, 682, 686,
648, 655, 689, 649, 655, 744, the data would be on Blocks 1 through 3 as follows:

BHDREYE  is an EYE-catcher to identlfy the start of the Block Header.
         It's value is always the characters 'HDR'

BHDRVER  Is a one-byte version indicator, used to enable backward
         compatability from future design versions. The current version is 1.

BHDRSEQ# is a one-byte sequence number, incremented each time the Block
         is written. When the counter reaches 256 it wraps back to zero.
         It is kept in sync with BFTRSEQ#. Whenever they are not equal,
         the Block has not been written completely and will be regarded
         as damaged.

BHDRFLGS is a one-byte flag field containing the Block type.
         For a data Block, the value is X'20'.

BHDR#REC is a one-byte field containing the number of records present
         in this Block. Five 686-byte records will fit on a 4K-Block.
         The number reflects the number of pointer entries on the Block.

BHDRXLVL is used only for index components. For an ESDS it contains zeros.

BHDRSELF is to double-check the file has not been damaged.
         it contains the Block's own XLRA - a 7-byte Block address
         with a byte of zeros appended.
         The first four bytes of zeroes are not shown in the table above.

BHDRNEXT points to the next logical Block on the Data Block chain.
         In an ESDS this should normally be the physical
         sequence of Blocks (with the exception of an occasional
         intermittent spacemap Block. Thus the Prefix Block field
         PFXBDATA points to Block 1 (Block 0 is a spacemap Block),
         Block 1 points to Block 2, Block 2 points to Block 3, etc.
         The last Block on the chain has foxes to indicate end of chain.
         The first four bytes of zeroes are not shown in the table above.

BHDRPREV points to the preceding logical Block on the Data Block chain.
         In an ESDS this should normally be the reversed physical
         sequence of Blocks (with the exception of an occasional
         intermittent spacemap Block. Thus the Prefix Block field
         PFXEDATA points to Block 3, Block 3 points to Block 2,
         Block 2 points to Block 1, which holds foxes to indicate end
         of chain. Block 0 is a spacemap Block and does not reside
         on the Data Block chain.
         The first four bytes of zeroes are not shown in the table above.

BHDRFRE@ is a three-byte pointer to the available freespace area in the Block.
         Since records are allocated starting from the end of the Block,
         the free space area starts after the pointer table's terminating entry.
         Block 1 holds 5 records, so the pointer table holds 6 entries of 4 bytes
         each. Freespace starts at 40 + 24 = 64 or X'40'.
         Block 2 holds 6 records, so the pointer table holds 7 entries of 4 bytes
         each. Freespace starts at 40 + 28 = 68 or X'44'.
         Block 3 holds 1 record, so the pointer table holds 2 entries of 4 bytes
         each. Freespace starts at 40 + 8 = 48 or X'30'.

BHDRFREE is a three-byte field holding the amount of available freespace in the Block.
         On Block 1 the freespace starts at offset 64 and the last record allocated
         starts at offset 620, leaving a free space of 620 - 64 = 556 or X'22C' bytes.
         On Block 2 the freespace starts at offset 68 and the last record allocated
         starts at offset 86, leaving a free space of 86 - 68 = 18 or X'12' bytes.
         On Block 3 the freespace starts at offset 48 and the only record allocated
         starts at offset 3344, leaving a free space of 3344 - 48 = 3296 or X'CE0' bytes.

--       The last two bytes of the header are unassigned and contain zeroes.

RPTRTBL  indicates the start of the pointer table.

RPTRTBL[0]
RPTRFLGS flags of first pointer. X'00' indicates a normal record pointer. 
RPTRREC@ pointer to first record's RDW on the Block.
         The first record is allocated 690 bytes (the record's length, plus 4 bytes
         for the record's RDW) down from the start of the Block Footer.
         4096 - 4 - 690 = 3402 or X'D4A'.
         On Block 2, the first record is 686 bytes long, so is allocated 690 bytes
         down from the Footer. 4092 - 690 = 3402 or X'D4A'
         On Block 3, the first record is 744 bytes long, so is allocated 748 bytes
         down from the Footer. 4092 - 748 = 3344 or X'D10'

RPTRTBL[1]
RPTRFLGS flags of second pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to second record's RDW on the Block.
         The second record is 695 bytes long, so it is allocated 699 bytes
         down from the preceding record. 3402 - 699 = 2703 or X'A8F'.
         On Block 2, the second record is 648 bytes long, so is allocated 652 bytes
         down from the preceding record. 3402 - 652 = 2750 or X'ABE'
         In Block 3 the value will be foxes to indicate the termination entry.

RPTRTBL[2] (Blocks 1 and 2 only, absent from Block 3)
         On Block 3 the third record has not yet been created, so here the
         value will be X'FF' = termination entry.
RPTRFLGS flags of third pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to third record's RDW on the Block.
         The third record is 712 bytes long, so it is allocated 716 bytes down
         from the preceding record. 2703 - 686 = 1987 or X'7C3'.
         On Block 2, the third record is 655 bytes long, so is allocated 659 bytes
         down from the preceding record. 2750 - 659 = 2091 or X'82B'

RPTRTBL[3] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS flags of fourth pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to fourth record's RDW on the Block.
         The fourth record is 677 bytes long, so it is allocated 681 bytes down
         from the preceding record. 1987 - 681 = 1306 or X'51A'.
         On Block 2, the fourth record is 689 bytes long, so is allocated 693 bytes
         down from the preceding record. 2091 - 693 = 1398 or X'576'

RPTRTBL[4] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS flags of fifth pointer. X'00' indicates a normal record pointer.
RPTRREC@ pointer to fifth record's RDW on the Block.
         The fifth record is 682 bytes long, so it is allocated 686 bytes down
         from the preceding record. 1306 - 686 = 620 or X'26C'.
         On Block 2, the fifth record is 649 bytes long, so is allocated 653 bytes
         down from the preceding record. 1398 - 653 = 745 or X'2E9'

RPTRTBL[5] (Blocks 1 and 2 only, absent from Block 3)
RPTRFLGS termination entry for table of record pointers. Value X'FF'
RPTRREC@ For Block 1, the next record is 686 bytes long, yet the Block has
         only 620 - 52 = 568 bytes of free space availalble. Therefore entry 5
         in the pointers table is the termination entry with value X'FFFFFF'
         On Block 2, the sixth record is 655 bytes long, so is allocated 659 bytes
         down from the preceding record. 745 - 659 = 86 or X'56'

RPTRTBL[6] (Block 2 only, absent from Blocks 1 and 3)
RPTRFLGS termination entry for table of record pointers. Value X'FF'
RPTRREC@ For Block 2, the the remaining freespace is less than required for the
         next record, so the table is terminated with an entry containing foxes.

--       The freespace area varies both in starting location and in length.
         The details are outlined above.

data[4]  fifth record, present on Blocks 1 and 2, not on Block 3
data[3]  fourth record, present on Blocks 1 and 2, not on Block 3
data[2]  third record, present on Blocks 1 and 2, not on Block 3
data[1]  second record, present on Blocks 1, 2, and 3
data[0]  first record, present on Blocks 1, 2, and 3

BFTREYE  is an EYE-catcher to identlfy the end of the Block.
         It's value is always the characters 'FTR'

BFTRSEQ# is a one-byte sequence number, incremented each time the Block
         is written. When the counter reaches 256 it wraps back to zero.
         It is kept in sync with BHDRSEQ#. Whenever they are not equal,
         the Block has not been written completely and will be regarded
         as damaged.

===================================================

--> Open

When the dataset is opened, the Prefix Block is read and validated.
The validations are described in the zVSAM_design document.

===================================================

--> Get (sequential)

When getting a record, the RPL holds the XLRA of the last record retrieved.
From the RPL's last XLRA the next RPTRTBL entry is located.
If the RPTRTBL entry is not a termination entry, the pointer is used
to retrieve the record and the record is returned to the application.

If a termination entry is encountered instead, then the Block's BHDRNEXT
pointer is used to access the next Block in the list of Data Blocks and the
first entry on that Block's pointer table is used to retrieve the next record.

--> Get (backward)

When getting a record, the RPL holds the XLRA of the last record retrieved.
From the RPL's last XLRA the preceding RPTRTBL entry is located if the XLRA has
a XLRAREC other than 0. If the XLRAREC is 0, the Block's BHDRPREV pointer is
used to access the preceding Block. Subsequently, that Block's BHDR#REC is used to
access the last logical record in that Block.
Either way, the record retrieved is returned to the application.

===================================================

--> Put (add new record)

The last Block on the chain of Data Blocks is accessed,
using the Prefix Block's PFXEDATA pointer.
If the Block is already in a buffer this step can be skipped.

A new record entry is allocated from the free-space area
and a new record pointer overwrites the existing termination
entry. A new termination entry is added to the table of record
pointers.

The Header is updated to reflect the decrease in free space:
BHDRFRE@ is incremented by 4 (the length of the new pointer table entry)
and BHDRFREE is decremented by the record length and the pointer table 
entry length.

If insufficient free space is available for allocating the new 
record, then a new Block is added to the end of the Data Block
chain. The full Block's BHDRNEXT pointer will be adjusted to point to
the new Block, the new Block's BHDRPREV will be set to point to the full
block, and the Prefix Block's PFXEDATA pointer will be set to point to the
new Block.
The remaining fields in the new Block's Header and Footer will be initialized,
and the first entry in the record pointer list will be created, followed
by a termination entry. The record can then be allocated right before the
Footer area of the Block.

The Spacemap Block covering the old Block will be updated to reflect the
Data Block being full. The spacemap Block covering the new Block (normally the
same Spacemap Block, but might be the next Spacemap Block) will be updated
to reflect that this Block is in use and partially filled.

--> Put (update existing record)

Case 1: length does not change
        The record in the Block is overwritten.
        No other changes are needed.

Case 2: length decreases
        The record is reallocated so that it still ends at the same address.
        Thus, its RDW will move up by the number of bytes the record has been
        shortened. The pointer in the pointer table is adjusted accordingly.
        Subsequently, all records allocated to a lower address than the
        updated record are moved up by the same number of bytes and their
        pointers are updated accordingly. Finally, the amount of free space
        is incremented by the number of bytes the record has been shortened.

Case 3: length increases, enough freespace is available.
        The old record is removed from the Block by moving all records residing
        at a lower offset than the record to be updated up by the old length of the
        record. Their record pointers are adjusted accordingly.
        The new version of the updated record is allocated from the enlarged
        freespace in the Block and its pointer adjusted to match its new location.
        The amount of freespace in BHDRFREE is decreased accordingly.
        Mark that the pointer to the record is not reallocated: it retains
        its position in the table of record pointers, thus its XLRA does not change.

Case 4: length increases, not enough freespace is available.
        Since the page does not have enough freespace to accomodate the new
        record, it will have to be stored in a different Block. But its XLRA is
        fixed until the next reload, and must remain valid to enable sequential
        access. Therefore the updated record is written at the end of the file,
        as if it were a new record. We call this a moved record.
        Its RPTRFLGS field is set to indicate it is a moved record.
        The old record is shrunk to 8 bytes, conforming to case 2 above.
        It is updated to contain the moved record's new XLRA.
        The updated old record (with the original XLRA) is called a displacement
        record. The displacement record is stored without a RDW; it's always
        8 bytes long. Its RPTRFLGS entry is updated to indicate that the record
        has been displaced off the Block.
        In the rare case where the old record is less than 8 bytes and therefore
        needs to be lengthened to 8 bytes, if enough freespace is available,
        that's no problem. If, however, not enough freespace is available
        then another record will be moved off the Block as well.
        It is impossible to create a situation where moving a longer record
        off the Block will not create enough room to hold both displaced records:
        A max of 256 displacement records occupies only 2K of storage.
        With a minimum Block size of 4K there is ample room to displace
        (extreme case) all records on the Block. Hence.
        
        A moved record is prefixed with an 8-byte XLRA that points back to
        the displacement record. Thus, should the moved record need to be
        displaced again, the moved record can be erased entirely and the
        displaced record can be updated to point to the new moved record's
        location.

        Alternatively, we might split the Block when it overflows.
        However, this would mean we'd be wasting nearly an entire Block
        of space. Since it's an ESDS, no new records will ever be allocated
        to either of the two resulting Blocks, while their joint content will
        be just over 1 Block's worth of data.
        In a Block-split scenario we're also facing issues as a result of
        changing teh XLRAs of all records moving from the full Block to
        its newly allocated sibling Block. Updating any and all AIXes,
        if they are defined over the ESDS cluster, comes to mind.

===================================================

--> Erase

Erase is not supported for ESDS datasetets.

To remove unneeded records, the dataset needs to be unloaded,
then reloaded with relevant data records only.

===================================================

--> Point

A point will set the indicated XLRA current. A subsequent sequential
read will return the the record with the indicated XLRA.
